### 1. Melhorias Estratégicas no Módulo de Importação de Scans

#### #004 – Módulo de Importação de Scans no Formato SBOM com Suporte a Versionamento de Esquemas

| **Campo** | **Detalhamento** |
| :--- | :--- |
| **ID** | #004 |
| **Título** | Implementação do módulo de importação de scans no formato SBOM com suporte a versionamento de esquemas (CycloneDX e SPDX) |
| **Tipo** | [X] Melhoria |
| **Módulo / Tela** | Importação de Scans – Novo submódulo SBOM |
| **Descrição Detalhada** | Este módulo visa estabelecer um pipeline robusto para a ingestão automatizada de arquivos SBOM (Software Bill of Materials). A solução deve suportar os principais padrões do mercado, como CycloneDX e SPDX, e contemplar um mecanismo de versionamento inteligente. Esse mecanismo permitirá que o sistema aplique lógicas de negócio e regras de validação distintas de acordo com a versão do schema informado, garantindo que mudanças estruturais nos padrões (ex: campos obrigatórios, nova nomenclatura de pacotes) sejam tratadas sem a necessidade de intervenção manual ou quebra de importações legadas. |
| **Justificativa (Melhoria)** | A crescente exigência regulatória internacional (como as diretrizes da ANPD, LGPD e normas de cibersegurança) demanda total transparência sobre a cadeia de suprimentos de software. Atualmente, o processo de análise de dependências é realizado de forma manual e descentralizada, inviabilizando a correlação rápida entre vulnerabilidades (CVEs) e os componentes de terceiros utilizados. A implementação deste módulo é essencial para a maturidade do DevSecOps na organização, reduzindo o tempo de resposta a riscos em supply chain. |
| **Comportamento Atual** | O sistema não possui qualquer recurso nativo para interpretar, validar ou armazenar dados oriundos de artefatos SBOM. A gestão de dependências ocorre em planilhas externas ou depende de ferramentas isoladas, sem integração com o repositório central de observações. |
| **Comportamento Esperado** | A plataforma deve disponibilizar uma interface dedicada (upload ou pull via URL) para recebimento do arquivo SBOM. Durante a importação, o usuário deverá selecionar a versão do schema utilizado (ex: CycloneDX v1.4, v1.5 ou SPDX 2.3). O sistema deve validar a estrutura, extrair metadados essenciais (componentes, versões, licenças e hashes) e integrá-los automaticamente à base de conhecimento, permitindo futuras consultas e correlações com vulnerabilidades detectadas em outros scans. |
| **Severidade / Prioridade** | Alta – A ausência deste recurso impede a rastreabilidade regulatória e expõe a organização a riscos legais e operacionais significativos em auditorias de segurança. |
| **Evidências** | (Aguardando matriz de exemplos de schemas SBOM e casos de uso para priorização dos primeiros parsers) |


#### #005 – Módulo de Importação de Scans no Formato SARIF com Suporte a Versionamento de Lógicas

| **Campo** | **Detalhamento** |
| :--- | :--- |
| **ID** | #005 |
| **Título** | Implementação do módulo de importação de scans no formato SARIF com suporte a versionamento de lógicas de processamento |
| **Tipo** | [X] Melhoria |
| **Módulo / Tela** | Importação de Scans – Novo submódulo SARIF |
| **Descrição Detalhada** | Trata-se da criação de um módulo capaz de ingerir arquivos de resultados no formato SARIF (Static Analysis Results Interchange Format), padrão OASIS amplamente adotado para interoperabilidade entre ferramentas de análise estática, segurança e qualidade de código. O módulo deve ser projetado com uma arquitetura de adaptadores versionados, permitindo que a equipe registre novas lógicas de transformação e enriquecimento de dados conforme o comitê SARIF publique revisões (ex: transição da versão 2.1.0 para futuras 2.2.0). Isso inclui a capacidade de mapear diferentes regras, níveis de severidade e localizações de código de maneira uniforme. |
| **Justificativa (Melhoria)** | A padronização via SARIF permite que a plataforma se torne um agregador universal de resultados de segurança, independentemente da ferramenta upstream (seja ela GitHub Advanced Security, CodeQL, Fortify, Checkmarx ou outras). Ao centralizar a importação sob um mesmo padrão, eliminamos a necessidade de criar parsers customizados para cada ferramenta do mercado, acelerando a adoção e reduzindo drasticamente o custo de manutenção do pipeline. |
| **Comportamento Atual** | Não há suporte à importação direta de arquivos SARIF. Cada ferramenta demandaria uma integração específica e isolada, o que inviabiliza a padronização e a comparação entre diferentes fontes de análise. |
| **Comportamento Esperado** | O sistema deve expor um endpoint ou área de upload para receber relatórios SARIF. A plataforma identificará a versão do schema (pelo campo `version` do JSON) e aplicará o processador correspondente. O resultado deve ser normalizado e persistido como observações padronizadas, exibindo detalhes como localização do código, mensagem do problema, nível de severidade e trilhas de correção, independentemente da ferramenta de origem. |
| **Severidade / Prioridade** | Média-Alta – Embora não seja um impeditivo imediato, sua implementação é estratégica para a escalabilidade e flexibilidade do ecossistema de segurança, sendo um pré-requisito para as integrações futuras. |
| **Evidências** | (Aguardando amostras de arquivos SARIF nas versões 2.1.0 e exemplos de extensões proprietárias para planejamento dos adaptadores) |


#### #006 – Módulo de Importação de Scans no Formato JSON do SonarQube com Conversão Automática para SARIF

| **Campo** | **Detalhamento** |
| :--- | :--- |
| **ID** | #006 |
| **Título** | Implementação de módulo para importação de scans no formato JSON do SonarQube com conversão automática para SARIF |
| **Tipo** | [X] Melhoria |
| **Módulo / Tela** | Importação de Scans – Submódulo SonarQube JSON Parser |
| **Descrição Detalhada** | Este módulo atuará como um tradutor especializado, projetado exclusivamente para processar relatórios gerados pela API do SonarQube ou pelo comando `sonar-scanner` em sua saída JSON. Ao invés de implementar uma lógica de persistência própria, a solução deve construir um mapper (tradutor) de campos que converta a estrutura hierárquica e as propriedades do SonarQube (ex: *bugs*, *vulnerabilities*, *code smells*, *hotspots*) para o formato SARIF 2.1.0. Após a conversão bem-sucedida, o sistema acionará automaticamente o módulo SARIF (#005) para realizar o processamento final, garantindo um fluxo unificado. |
| **Justificativa (Melhoria)** | Muitas organizações possuem uma base histórica massiva de relatórios do SonarQube e dependem de suas métricas para tomada de decisão. Esta melhoria permite a migração gradativa destes clientes para a nova plataforma sem perda de dados, reaproveitando todo o conhecimento acumulado sobre regras e padrões já configurados no SonarQube. Além disso, ao converter para SARIF, o módulo herda automaticamente todas as evoluções futuras do processador SARIF, evitando duplicidade de esforços e garantindo consistência na base de observações. |
| **Comportamento Atual** | Não existe nenhum mecanismo de ingestão para o JSON do SonarQube. Clientes que desejam migrar seus dados precisariam recorrer a scripts manuais não oficiais, sujeitos a erros de mapeamento e sem validação de integridade. |
| **Comportamento Esperado** | O usuário poderá enviar um arquivo JSON exportado do SonarQube. A plataforma validará o schema do arquivo, aplicará o mapeamento de severidades (ex: *BLOCKER* para *Critical*; *MAJOR* para *High*), associará as regras do Sonar ao identificador correspondente no SARIF e, por fim, delegará ao módulo #005 o armazenamento e a indexação dos dados. O resultado final será uma observação enriquecida e plenamente funcional dentro do ecossistema da ferramenta. |
| **Severidade / Prioridade** | Média – Puramente estratégica para facilitar a adoção por novos clientes e reduzir barreiras de entrada, sendo particularmente valiosa para ciclos de POC (Prova de Conceito) em grandes contas corporativas. |
| **Evidências** | (Aguardando especificação oficial do schema JSON do SonarQube para as versões LTS atuais, para definição do mapeamento mais fidedigno) |


#### #007 – Módulo de Importação de Scans no Formato VEX com Suporte a Versionamento de Lógicas

| **Campo** | **Detalhamento** |
| :--- | :--- |
| **ID** | #007 |
| **Título** | Implementação do módulo de importação de scans no formato VEX com suporte a versionamento de lógicas de análise |
| **Tipo** | [X] Melhoria |
| **Módulo / Tela** | Importação de Scans – Novo submódulo VEX |
| **Descrição Detalhada** | O formato VEX (Vulnerability Exploitability eXchange) é um padrão emergente da CISA para comunicar o status de explotabilidade de vulnerabilidades em produtos de software. Este módulo tem como objetivo ingerir arquivos VEX (normalmente em formato JSON ou OpenVEX) e interpretar suas declarações de status (ex: *affected*, *fixed*, *under_investigation*, *not_affected*). A solução deve prever um sistema de versionamento para lidar com as evoluções do esquema OpenVEX e com as variações impostas por diferentes fornecedores, permitindo que o administrador cadastre novas regras de validação e extração conforme os padrões amadureçam. |
| **Justificativa (Melhoria)** | O VEX é o principal veículo para operacionalizar a gestão de risco baseada em vulnerabilidades conhecidas (KBV). Ao importar dados VEX, a plataforma consegue distinguir automaticamente uma vulnerabilidade crítica que é explorável (prioridade máxima) de uma vulnerabilidade crítica que, apesar da nota CVSS alta, não afeta o contexto da aplicação (prioridade reduzida). Essa inteligência contextual é vital para evitar a fadiga de alertas e otimizar o trabalho dos times de resposta a incidentes. |
| **Comportamento Atual** | O sistema trata todas as vulnerabilidades com o mesmo peso, sem considerar o contexto de explotabilidade ou status de correção declarado por fornecedores, resultando em um grande volume de falsos positivos ou ruídos desnecessários para o desenvolvedor. |
| **Comportamento Esperado** | A plataforma deve receber o arquivo VEX, processar suas declarações e cruzar essas informações com as observações já existentes (provenientes de SBOM e SARIF). Com base nesse cruzamento, o sistema deve recalcular dinamicamente a prioridade da observação, sinalizar se uma correção já está disponível ou se o componente afetado foi removido, fornecendo ao usuário uma visão clara e acionável do que realmente precisa ser remediado. |
| **Severidade / Prioridade** | Média-Alta – Fundamental para a evolução da plataforma para um sistema de gestão de vulnerabilidades baseado em risco (RBVM), agregando um valor diferencial significativo em relação às soluções concorrentes que ignoram o contexto de explotabilidade. |
| **Evidências** | (Aguardando definição das versões iniciais do OpenVEX e exemplos de VEX statements fornecidos por grandes fornecedores de software para modelagem dos parsers) |


#### #008 – Revisão e Otimização da Busca de Padrões SAST via Azure Search Code

| **Campo** | **Detalhamento** |
| :--- | :--- |
| **ID** | #008 |
| **Título** | Revisão e otimização do motor de busca de padrões SAST utilizando Azure Search Code para aprimorar a precisão e o desempenho das consultas |
| **Tipo** | [X] Melhoria |
| **Módulo / Tela** | Mecanismo de Indexação e Busca – Azure Cognitive Search / Azure Code Search |
| **Descrição Detalhada** | Atualmente, a ferramenta utiliza o Azure Search Code para realizar a correlação entre as observações geradas e os padrões SAST cadastrados, permitindo identificar trechos de código vulneráveis. Contudo, com o crescimento exponencial da base de código e a evolução contínua dos patterns, o mecanismo atual apresenta latência elevada, baixa relevância nos resultados retornados (recall insuficiente) e incapacidade de interpretar semânticas avançadas, como análises de fluxo de dados ou contextos de escopo. Esta melhoria propõe uma revisão profunda da arquitetura de busca, incluindo a otimização dos índices, a reavaliação dos pesos de campo (boosting), a implementação de filtros híbridos (busca por léxico combinada com análise sintática básica) e a adoção de estratégias de caching inteligente para consultas recorrentes, garantindo que a plataforma escale para repositórios de grande porte sem degradação de performance. |
| **Justificativa (Melhoria)** | O tempo de resposta e a precisão das buscas de padrões são fatores críticos para a adoção contínua da ferramenta pelos times de desenvolvimento. Em cenários de CI/CD com milhares de regras a serem avaliadas, a demora na busca inviabiliza a integração contínua, gerando filas de processamento e atrasos no feedback aos desenvolvedores. Além disso, uma busca mal otimizada resulta em falsos negativos (vulnerabilidades não detectadas) e falsos positivos excessivos, minando a confiança do usuário na solução. |
| **Comportamento Atual** | O sistema realiza buscas textuais basicas sobre os índices do Azure, sem a aplicação de técnicas avançadas de relevância, como refinamento por proximidade de tokens ou ponderação dinâmica baseada na criticidade do pattern. A ausência de um plano de partição e roteamento inteligente faz com que consultas complexas atinjam tempos de timeout em projetos monolíticos extensos. |
| **Comportamento Esperado** | A plataforma deve implementar um novo pipeline de consulta que inclua: reindexação periódica com mapeamento semântico enriquecido; introdução de scoring profiles customizados; suporte a queries parametrizáveis por linguagem de programação e tipo de vulnerabilidade; e um sistema de monitoramento contínuo dos SLAs de busca (sub 2 segundos para 95% das consultas). Os resultados devem ser ranqueados por relevância contextual, priorizando padrões que realmente se aplicam ao escopo do código analisado. |
| **Severidade / Prioridade** | Alta – A performance e a acurácia do mecanismo de busca impactam diretamente todos os módulos subsequentes (geração de observações, dashboards e relatórios), sendo um gargalo crítico para a experiência do usuário final. |
| **Evidências** | (Aguardando relatórios de telemetria atuais do Azure Search, incluindo métricas de latência por tipo de consulta, para embasar o plano de otimização e definir os novos thresholds de performance) |


#### #009 – Implementação de Extensões para Integração API-First com Ferramentas de Segurança e Análise de Dados

| **Campo** | **Detalhamento** |
| :--- | :--- |
| **ID** | #009 |
| **Título** | Desenvolvimento de um framework de extensões para integração nativa via API REST com ferramentas de segurança (SonarQube, Dependency Track, Defect Dojo, SecObserve e outros), possibilitando ingestão e análise automatizada de dados em tempo real |
| **Tipo** | [X] Melhoria |
| **Módulo / Tela** | Módulo de Integrações Extensíveis – API Gateway e Conectores |
| **Descrição Detalhada** | Propomos a criação de uma arquitetura orientada a conectores (plugáveis) que permita à plataforma consumir dados diretamente das APIs públicas das principais ferramentas do ecossistema AppSec. Este framework não se limitará à importação estática de arquivos (como os módulos anteriores de SBOM, SARIF, VEX e SonarQube JSON), mas sim estabelecerá um canal bidirecional de comunicação: a ferramenta poderá puxar (pull) resultados de scans programados, receber (push) webhooks de finalização de análise e, em cenários avançados, até mesmo disparar novas análises remotamente. Cada conector será desenvolvido seguindo uma interface padronizada, contemplando autenticação segura (OAuth2, API Keys), gerenciamento de rate limits, tratamento de erros e mapeamento dos dados de entrada para o modelo unificado de observações da plataforma. |

Exigir que o usuário exporte arquivos manuais a cada nova análise é um processo arcaico, propenso a falhas e que inviabiliza a adoção em larga escala. A integração nativa via API elimina o atrito operacional, permitindo que a plataforma atue como um agregador inteligente, centralizando a visibilidade sem substituir as ferramentas já consolidadas nas esteiras de DevOps. |
| **Comportamento Atual** | A plataforma depende exclusivamente do upload manual de arquivos para ingerir dados de fontes externas (conforme descrito nos itens #004 a #007). Não existe qualquer mecanismo de sincronização automática ou consumo de eventos oriundos de ferramentas terceiras. |
| **Comportamento Esperado** | O administrador poderá acessar uma nova seção "Integrações" no painel de configurações, escolher a ferramenta desejada na lista de conectores disponíveis (ex: SonarQube, Dependency Track, Defect Dojo, SecObserve), informar as credenciais de API e a URL do endpoint, e configurar a frequência de sincronização (ex: a cada 6 horas, ou sob demanda via webhook). A partir deste momento, a plataforma passará a consumir os dados automaticamente, enriquecendo a base de observações com as vulnerabilidades encontradas, status de correção e métricas de densidade de defeitos, tudo de forma totalmente transparente para o usuário final. |
| **Severidade / Prioridade** | Média-Alta – Embora não seja um bloqueio funcional imediato, a implementação deste módulo é um divisor de águas para a escalabilidade comercial da solução, reduzindo drasticamente o custo de adoção e aumentando a retenção de clientes ao oferecer valor imediato com poucos cliques. |
| **Evidências** | (Aguardando documentação das APIs públicas das ferramentas listadas, especialmente os schemas de autenticação e os endpoints de *observations* e *findings*, para a elaboração dos primeiros conectores piloto) |


### 2. Sugestões de Novas Integrações via API para Extensões Futuras

Para maximizar o valor estratégico do framework de extensões (#009), sugerimos que os seguintes conectores sejam planejados para as próximas fases do roadmap, complementando as ferramentas já citadas pelo solicitante:

- **Snyk**: Para ingestão de vulnerabilidades em dependências de código aberto, containers e IaC, utilizando sua API de *reports* e *observations*.
- **Veracode**: Integração com a API de *findings* e *mitigation* para consolidar resultados de SAST, DAST e SCA da plataforma Veracode.
- **Checkmarx (CxSAST / CxSCA)**: Consumo dos resultados de *scans* e *queries* via API REST, mapeando severidades e caminhos de execução.
- **Fortify (Micro Focus / OpenText)**: Conexão com o Fortify SSC (Software Security Center) para extrair *observations* e *artifacts* de análises estáticas e dinâmicas.
- **AWS Inspector**: Para ambientes cloud-native, integração que permita consumir os achados de vulnerabilidades em instâncias EC2, ECR e Lambda.
- **GCP Cloud Security Command Center (SCC)**: Sincronização de *findings* de segurança provenientes de diversos serviços Google Cloud, centralizando a visibilidade.
- **Aqua Security / Trivy Server**: Para monitoramento contínuo de imagens de containers em runtime e em registries privados.
- **Black Duck (Synopsys)**: API de *components* e *vulnerabilities* para aprofundar a análise de supply chain e licenciamento.
- **GitLab Security Dashboard**: Consumo via API GraphQL do GitLab para importar resultados de *Security Scans* (SAST, DAST, Container Scanning) realizados dentro da esteira nativa do GitLab.
- **Jenkins (via Plugin ou REST API)**: Para disparar workflows de importação automaticamente ao final de jobs de *build*, garantindo feedback instantâneo no pipeline.
- **ThreadFix / DefectDojo (já citado)**: Para bidirecionalidade, permitindo que a plataforma atue tanto como fonte de dados quanto como consumidora de achados consolidados.
- **Azure DevOps (ADO)**: Integração com a API de *Work Items* e *Test Results* para correlacionar vulnerabilidades com tarefas de correção já existentes no backlog.

A adoção dessas integrações posicionará a plataforma como um hub universal de inteligência em segurança, eliminando silos de dados e promovendo uma cultura de remediação baseada em dados consolidados e confiáveis.


### 3. Sugestões de Novos Formatos a Serem Considerados para Futuros Ciclos

Além dos formatos já listados, recomendamos a análise e planejamento para inclusão dos seguintes padrões em sprints subsequentes, visando expandir a capilaridade da plataforma:

- **OWASP Dependency Check JSON**: Formato nativo da ferramenta de análise de dependências da OWASP, amplamente utilizado em pipelines CI/CD.
- **Trivy JSON (Result)**: Saída do scanner de vulnerabilidades para containers, dependências e código IaC.
- **GitLab SAST JSON**: Padrão específico de relatórios gerados pelo GitLab Secure, comum em ambientes que já utilizam a esteira do GitLab.
- **JFrog Xray JSON**: Estruturado para integração com repositórios de artefatos e análise de componentes binários.
- **DefectDojo JSON/CSV**: Visando integração com plataformas agregadoras de vulnerabilidades para gestão centralizada do ciclo de vida das correções.
- **CSAF (Common Security Advisory Framework)**: Padrão da OASIS para compartilhamento de avisos de segurança, complementar ao VEX para atualizações de *patch* e boletins oficiais.

A adoção destes formatos, quando combinada com os módulos base (SARIF e SBOM), posicionará a ferramenta como um hub universal de segurança para qualquer stack tecnológico.


### 4. Melhorias Estratégicas de Internacionalização (i18n) 

#### #010 – Implementação de Internacionalização (i18n) com Detecção Automática de Idioma e Configuração Personalizada no Perfil do Usuário

| **Campo** | **Detalhamento** |
| :--- | :--- |
| **ID** | #010 |
| **Título** | Implementação de internacionalização (i18n) com detecção automática de idioma pelo navegador e opção de escolha durante o onboarding e no perfil do usuário (Settings/Profile/User) |
| **Tipo** | [X] Melhoria |
| **Módulo / Tela** | Global – Camada de internacionalização da aplicação; Fluxo de Onboarding; Módulo de Configurações (Settings/Profile/User) |
| **Descrição Detalhada** | Esta melhoria visa tornar a plataforma acessível e amigável para usuários de diferentes nacionalidades, através da implementação de um sistema completo de internacionalização (i18n). A solução deve atuar em três frentes principais. Primeiramente, na detecção automática do idioma preferido do cliente, utilizando o cabeçalho `Accept-Language` enviado pelo navegador, com um fallback inteligente para o idioma padrão (inglês) caso a preferência não seja suportada. Em segundo lugar, durante o fluxo de onboarding, imediatamente após o registro inicial do usuário, a plataforma deve exibir uma tela de seleção de idioma, permitindo que o novo usuário escolha explicitamente a língua em que deseja interagir com o sistema, garantindo que a experiência desde o primeiro acesso seja totalmente localizada. Por fim, a configuração deve ser persistente e editável a qualquer momento no perfil do usuário, acessível via Settings/Profile/User, onde o usuário pode alterar sua preferência linguística a qualquer momento, com a plataforma aplicando a mudança em tempo real sem necessidade de novo login. A implementação técnica deve prever um repositório centralizado de arquivos de tradução (JSON ou similar), suporte a pluralização, formatação de datas, números e moedas de acordo com o locale, e mecanismo de cache para otimização do carregamento das traduções. |
| **Justificativa (Melhoria)** | A internacionalização é um requisito fundamental para a escalabilidade global do produto. Atualmente, a plataforma é monolíngue, o que limita severamente sua adoção em mercados internacionais e reduz a experiência do usuário para equipes multinacionais que compartilham a mesma ferramenta. A falta de suporte a múltiplos idiomas também pode ser um impeditivo em processos de conformidade regulatória em países que exigem interfaces em idioma nativo para determinados setores. Além disso, a detecção automática e a escolha no onboarding eliminam atritos iniciais, aumentando a taxa de conversão e a satisfação dos novos usuários, enquanto a opção de ajuste no perfil oferece flexibilidade para equipes globais que compartilham a mesma instância da plataforma. |
| **Comportamento Atual** | O sistema é completamente monolíngue, com todas as interfaces, mensagens, notificações e rótulos apresentados em um único idioma (atualmente, português do Brasil). Não existe qualquer mecanismo de detecção de preferência linguística, nem opção de alteração no perfil ou durante o fluxo de cadastro. |
| **Comportamento Esperado** | A plataforma deve, ao receber uma requisição de um novo visitante, identificar o idioma preferido via cabeçalho `Accept-Language` e renderizar a interface correspondente (ex: inglês, espanhol, francês, etc.) sempre que houver suporte. Durante o onboarding, o usuário visualizará uma tela de seleção de idioma com as opções disponíveis, podendo escolher ou confirmar a detecção automática. Esta escolha será armazenada no perfil do usuário e aplicada em todas as sessões futuras. No painel de configurações (Settings/Profile/User), o usuário poderá alterar seu idioma a qualquer momento, com a interface sendo atualizada dinamicamente sem recarregamento completo da página. Todas as strings da aplicação, incluindo mensagens de erro, notificações, labels de formulários, cabeçalhos, rodapés e conteúdos de ajuda, devem estar externalizadas em arquivos de tradução, organizados por módulo e atualizáveis via CI/CD. |
| **Severidade / Prioridade** | Média-Alta – Embora não bloqueie as funcionalidades essenciais, esta melhoria é crítica para a expansão comercial e a competitividade global da solução, sendo frequentemente um dos primeiros requisitos levantados em processos de internacionalização de clientes corporativos. |

### 5. Plano de Idiomas Iniciais e Roadmap de Tradução

Para a implementação da internacionalização, recomenda-se que os seguintes idiomas sejam priorizados na primeira fase, com base na penetração de mercado e na base de clientes existente:

- **Inglês (Estados Unidos)**: `en-US` – idioma padrão para fallback e principal público-alvo.
- **Português (Brasil)**: `pt-BR` – idioma atual do sistema, mantido como nativo.
- **Espanhol (Espanha)**: `es-ES` – amplamente utilizado em mercados da América Latina e Europa.
- **Francês (França)**: `fr-FR` – relevante para mercados europeus e africanos francófonos.
- **Alemão (Alemanha)**: `de-DE` – importante para o mercado corporativo europeu.

A estratégia de tradução deve contemplar a utilização de ferramentas de CAT (Computer-Assisted Translation) integradas ao pipeline de desenvolvimento, garantindo a consistência terminológica e a atualização ágil à medida que novas funcionalidades forem entregues. Recomenda-se ainda a criação de um glossário centralizado para termos técnicos de segurança (ex: "vulnerability", "exploit", "remediation", "pattern") que devem ser traduzidos de forma padronizada em todos os idiomas.
